## New findings

**F1 — Surface-drop orientation is unbound, so validity and rendering can disagree on the flagship case.**
- Severity: **Major**
- Affected Scope: §8.1 footprints (lines 307–309), §8.2 (lines 327–350, surface location kind line 345), A6 (lines 252–255); CC-003/CC-004/CC-005 contracts.
- Simplicity Rationale: The plan pins two book footprints per orientation (flat 0.20 × 0.32 × 0.05; upright — corrected — 0.20 × t × h, `assets.ts:407,411`) but never says which applies to a `kind:'surface'` placement. Today orientation is a view-side function of slot membership (`gameView.ts:111-114`: `inSlot ? 'upright' : 'flat'`); the new surface location stores only `{surfaceId, x, y, rotation}` (§8.2:345) — no orientation field, no binding rule. Naive extension renders tier-dropped books **flat** while validity may assume upright (or vice versa): a flat book's 0.32 depth checked as a 0.10-wide upright footprint will pass between 0.30-spaced slot books (`CC-010.md:18`) yet interpenetrate them on screen — the exact "book on a shelf tier" case R1 (line 117) and CC-006 sell. Mitigation is one contract sentence plus one named pure test: bind surface-drop orientation (e.g., flat-by-default on furniture surfaces, or store orientation in the location kind) and derive `validateSurfaceDrop`'s footprint from it. No new machinery — it closes a hole in the existing data contract.

**F2 — The e2e debug hook cannot express the new location kind; every planned "re-drag from a surface" test mis-aims.**
- Severity: **Major**
- Affected Scope: §8.3 step 4 (line 366–368), CC-005 (drag pipeline), CC-006 acceptance 5 ("re-dragged … from shelf and from counter"), CC-016 ("Re-dragging placed items: shelf → counter → back").
- Simplicity Rationale: `window.__cozy.itemClientPos` maps only `slot` / `floor` / `held` and falls through to `{0,0,0}` otherwise (`gameView.ts:415-421`); `scripts/e2e.cjs:47` uses it as the drag **origin** for every scenario. Once items can rest on surfaces, every planned surface re-drag test starts from the SVG origin — the harness either fails or "passes" while testing nothing. The plan's otherwise exhaustive location-kind checklist (§8.2 restore semantics, §8.13) never mentions the hook. Mitigation: one branch in CC-005 (surface kind → `(x, y, SurfaceDef.topZ)`), keeping the hook read-only. Cheap, but it must be in the contract before CC-006/CC-016, not discovered mid-verification.

**F3 — The recommended depth-order fix needs a support-relative key, not the existing `x + y` key; otherwise the fix itself hides items on D6's marquee surfaces.** *(New evidence that changes the shape of the already-agreed structural fix.)*
- Severity: **Major**
- Affected Scope: §8.6 mitigation (lines 414–416), §8.13 risk row 2 (line 573), §8.9 Option A (line 460); CC-005/CC-010/CC-013 contracts.
- Simplicity Rationale: Prior stages converged on merging props+items into one depth-sorted paint list "with a shared depth key (+ sortBias)". New geometry check: a surface-placed item's geometric `x + y` is routinely **below** its support's anchor depth — the countertop spans world x 6.26–9.34 (`assets.ts:318`) against anchor depth 7.8+0.36 = 8.16, so a mug at x 6.5 keys 6.86; a book on a shelf tier at y 1.3 keys 1.6 vs shelf anchor 2.2−0.5 = 1.7 (`house.level.ts:32`, `CC-010.md:34`). A merged list keyed on plain `x+y` (the current per-item key, `gameView.ts:147,152`, which also ignores z) would paint the counter and bookshelf **over** items resting on them — silently regressing free placement on exactly the surfaces the upgrade is about. The merged key must be support-relative (item on furniture F takes `depth(F) + ε`; floor items keep `x+y`); one sentence in CC-005's contract, still a single sort, no new layer. This also confirms §8.9's "one-line change behind `depth()`" is optimistic: there are two depth implementations to retire (`projection.ts:49` vs the hardcoded key in `gameView.ts`), as stage 5 noted — the merge should unify them.

**F4 — A9's default clearance is geometrically wrong over the counter (mug-rack underside), latently.**
- Severity: **Nit**
- Affected Scope: A9 (lines 260–261), §8.1 registry (lines 312–314), CC-003.
- Simplicity Rationale: Default `clearance = wallHeight − topZ` gives the counter 2.9 − 0.96 ≈ 1.94, but the mug-rack board hangs at z 1.32–1.46 (`assets.ts:296`) over most of the countertop's x-range — real clearance ≈ 0.36. A tallest book (mustard, h 0.36, `assets.ts:400`) dropped under the rack grazes the art today; any future taller item breaks invisibly. One sentence in CC-003 (pin the counter's clearance to the rack underside) — no schema change needed.

**F5 — `kind: 'mat'` violates the declared `SurfaceDef` union, and the mat's win-rule consequence is unstated.**
- Severity: **Nit**
- Affected Scope: §8.1 schema (line 293) vs CC-003 line 31 ("kind `mat`, walkable"); §8.4 win rule (line 387–389).
- Simplicity Rationale: CC-002/§8.1 declare `kind: 'floor' | 'furniture'`; CC-003's entry-mat entry uses a third value — schema drift between two foundation tickets. Separately, registering the mat (topZ ≈ 0.02, functionally floor) as a surface means a mat rest satisfies tidy-all's "not floor" while the identical spot 0.1 units off the mat does not. That may be intended (the shoes' home *is* the mat), but the plan never says it; one sentence in CC-007. Walkability itself is already data-driven (mat/rug simply absent from CC-003's exclusion AABB table) — no `walkable` flag should be added (YAGNI).

**F6 — Slot ghost and surface ghost simultaneity is unspecified.**
- Severity: **Nit**
- Affected Scope: §8.3 (lines 370–371 "Existing slot aiming … untouched") vs CC-005 (`ghostBySurface` "alongside existing `ghostBySlot`").
- Simplicity Rationale: Every bookshelf tier hosts both slots and a surface, so a single drag near the shelf can legitimately light up a slot ghost **and** a tier fit/no-fit ghost at once. Target *resolution* precedence is the prior catalyst finding; this is the presentation twin. One sentence in CC-005 (slot ghost wins when a slot is targeted; surface ghost otherwise) — otherwise two tickets implement two independent ghost systems that visibly collide.

## Directive verdict — elevated surfaces, depth, coordinates, resize, and no new machinery

**1. No unnecessary physics / engine / rotation — PASS (with the one previously-flagged exception).** §8.2's validity is four plain AABB predicates (bounds, clearance, ε-overlap, furniture exclusion) in the already-pure model — the minimum set expressing R1's examples; no rigid bodies, no simulation step, no engine. The solver and reachability validators are test-time only (CC-013 exports, CC-015 runs ≥100 seeds) — not runtime physics. Rotation is deferred with zero tickets (A6, §4:201–205, §8.9 closes with "No tickets are created for either option"). The single YAGNI exception remains `findSurfaceAt` (dead API with a filter that excludes the counter/linen/bookshelf tiers) — delete it rather than repair it, since §8.3's `data-surface` walk already selects the surface. Code search confirms no existing PRNG/AABB/scatter utility is being reinvented; `data-surface` correctly follows the established `data-item-id`/`data-slot` pattern (`gameView.ts:318`, `scene.ts:183,195`).

**2. Elevated-surface aiming — architecture holds; the gap is a contract amendment, not a structural fix.** The `data-surface` selection mechanism is sound — verified geometrically that the rebuilt shelf's tier top faces **never overlap on screen** (tier top-face overlap requires `xu − xl = 0.6` but the shelf interior is only 0.44 deep, `CC-010.md:34` vs 0.60 gaps), so the plan's "kills the tier ambiguity" claim survives scrutiny; aim-through-props (plant in front of the shelf) resolves correctly by stack-walking. The remaining gap is exactly prior M2: the plan states the compensation convention for slots only (`carryZ − slotZ`, `model.ts:147-148`) and never for surfaces, and `findSurfaceAt`'s height filter contradicts R1. Correct response at plan altitude: **contract amendment** — generalize the existing slot-compensation pattern to `carryZ − topZ`, define `validateSurfaceDrop`'s inputs as compensated floor coordinates, delete/repair `findSurfaceAt`, and add the counter-aim e2e case. Note the plan's own named e2e case is the forcing function: the existing `dragTo` aims at the *projected* surface point (`e2e.cjs:48,74,99`), which floor-maps to an uncompensated point outside the counter's bounds — the convention must be fixed for the planned test to be implementable at all.

**3. Depth order — the prior structural-fix verdict stands and is refined by F3; acceptance criteria alone are insufficient.** Cross-layer paint depth (`scene.ts:219` fixed layer order, `README.md:101-103`'s revoked mitigation) cannot be patched by CC-010's screenshot checks, because seeded scatter makes the overlap space unbounded — screenshots sample it, seeded layouts redefine it every run. The correct plan-altitude response is the **structural fix** (one merged depth-sorted paint list, rebuilt on state change, ~40 nodes) with the support-relative key from F3. Everything else about the render pipeline (ghosts/labels/drag as intentional overlays) survives unchanged.

**4. Coordinate conversion — already sound; nothing to add beyond the aiming amendment.** Room units end-to-end are verified (`types.ts:4-8` docblock, `projection.ts:30-39` exact `toScreen`/`toFloor` inverse, no screen-space data anywhere in level/model). Surface placements reuse the same discipline (`DropTarget`/location kind in room units, settle to `(x, y, topZ)`).

Resizing — already covered; no new work.** Conversion is CTM/viewBox-based (`gameView.ts:173-186`), the existing e2e has a live resize-then-drag step (`e2e.cjs:142-149`), and CC-016 extends it; `elementsFromPoint` operates in client space and is scale-independent, and pointer capture keeps drags alive over the HUD. No finding.

**6. Every open item resolves as either a contract amendment (shelf-clean rule wording → B1; occupancy ledger → M1; aiming convention → M2; static-prop carve-outs → M3; solver fidelity → stage-5 #4) or the one contained view structural fix (paint depth).
